# Slotfolio

Новый самостоятельный проект на Next.js 16 App Router, React 19 и TypeScript. Каталог, редакционные разборы и справочник об устройстве слотов. Старый Slotfolio не использовался.

## Запуск

Требуется Node.js 20.9+ (проект проверен на Node 24).

```sh
npm ci
npm run dev
```

На Windows PowerShell при запрете npm.ps1 используйте `npm.cmd`.

Сайт: http://localhost:3000. Производственная версия: `npm run build`, затем `npm start`.

## Что реализовано

- Редакционная главная с основной историей, боковой полосой, игровым указателем и тематическими входами.
- Каталог подготовлен к базе 1000+ игр: серверная часть формирует компактный индекс и готовые счётчики фильтров, а браузер получает только поля, нужные каталогу. Поиск, комбинированные фильтры, сортировка и порционная выдача по 18 игр работают без передачи полных досье в клиентский JavaScript. Параметры сохраняются в URL.
- Тридцать полных досье игр: несколько механик, отдельные блоки функций и бонусов, математический профиль, подтверждённые RTP-конфигурации и максимумы там, где они опубликованы провайдером, редакционный контекст, источники, FAQ и связанные игры.
- Сравнение двух игр с механиками, особенностями, RTP-конфигурациями, подтверждёнными максимумами и сохранением выбора в localStorage.
- Пять полноценных справочников механик и семь редакционных профилей провайдеров: вычисляемые сводки по текущей выборке, характерные игры, связанные принципы, фильтрованный каталог и быстрый переход в сравнение.
- Тематическая подборка, длинная статья, отдельный гайд о RTP и объяснение бонусных условий.
- GEO-пример для Великобритании, страница проекта, редакционная политика, прозрачность партнёрства, конфиденциальность, ответственная игра.
- Loading, error, 404, favicon, skip link, клавиатурный фокус.
- SEO-каркас: canonical URL, Open Graph / Twitter metadata, sitemap.xml, управляемый robots.txt и JSON-LD для сайта и игровых досье.

## Архитектура

`src/app` — маршруты и серверные шаблоны. `src/lib/data.ts` — полные типизированные досье и связи. `src/lib/catalog-index.ts` на сервере преобразует их в компактный каталог и заранее считает facets; `src/lib/catalog-query.ts` содержит клиент-безопасную логику поиска, фильтрации и сортировки без импорта полного `data.ts`. `src/components/catalog.tsx` получает только компактную модель. Сравнение вынесено в `src/components/comparison.tsx`, а ограничение выбора хранится в небольшом `compare-button.tsx`, поэтому кнопки сравнения больше не тянут весь каталог в клиентский bundle. `src/lib/dossier.ts` хранит редакционные feature cards и отдельно верифицированные числовые параметры. `src/components/editorial.tsx`, `shell.tsx` и `globals.css` отвечают за визуальную систему.

Такая схема рассчитана на статический каталог порядка 1000–3000 игр без обязательного backend: в браузер не попадают длинные тексты досье, источники и редакционные заметки, которые каталогу не нужны. Поиск использует заранее нормализованный компактный индекс, фильтры мемоизированы, ввод поиска проходит через `useDeferredValue`, а карточки рендерятся порциями по 18. Для десятков тысяч игр уже стоит отдельно оценивать серверную БД/поисковый индекс, но 1000 игр сами по себе не требуют смены хостинга.

## Индексация и SEO

Канонический адрес задаётся через `NEXT_PUBLIC_SITE_URL`. Для GitHub Pages workflow подставляет адрес репозитория автоматически. Поисковая индексация намеренно выключена, пока `NEXT_PUBLIC_INDEXABLE` не равен `true`.

При `NEXT_PUBLIC_INDEXABLE=false` корневые metadata и `robots.txt` запрещают индексирование. После финальной проверки можно создать repository variable `NEXT_PUBLIC_INDEXABLE=true` в GitHub и пересобрать Pages: `robots.txt` переключится на `Allow: /` и добавит ссылку на `/sitemap.xml`. `/search` и `/compare` останутся `noindex`, чтобы не плодить поисковые и персональные состояния как отдельные страницы.

Досье игр получают canonical, Open Graph / Twitter metadata и JSON-LD `Article` + `Game` + `BreadcrumbList`. Sitemap строится из фактических данных `slots`, `mechanics`, `providerProfiles` и системных страниц, поэтому новые сущности автоматически попадают в него после сборки.

## Изображения игр

Все игровые изображения публикуются локально. В v123 удалены старые дубли PNG/WebP из `public/images`: единственный рабочий набор находится в `public/images/slots`, а стандартная Open Graph-картинка тоже использует локальный WebP. Сейчас 31 игровой WebP занимает около **1,16 МиБ**, в среднем около **38 КБ на файл**.

Политика для массового наполнения: обычная обложка ограничивается 960×540, крупная редакционная/OG-графика — 1200×630. Локализатор кодирует WebP адаптивно (стартовое качество 76 с понижением при тяжёлом исходнике) и держит нормальную обложку в разумном весовом коридоре. При нынешнем среднем весе 1000 изображений — это ориентировочно около 40 МиБ, а не сотни мегабайт.

`docs/image-sources.json` остаётся журналом происхождения. Загрузка внешних исходников теперь **не выполняется автоматически при production build**: `prebuild` только проверяет, что все локальные файлы уже на месте, декодируются, не превышают заданные размеры и вес. Это важно для GitHub Pages — сборка 1000 игр не должна зависеть от тысячи сетевых запросов к сайтам провайдеров.

Для добавления новых изображений используется отдельный шаг:

```sh
npm run assets:localize
npm run assets:verify
```

Локализатор использует прямой image URL или `og:image`/`twitter:image` официальной страницы, сохраняет WebP по пути `local` из manifest и кэширует исходник только как рабочий build-time ресурс. Runtime никогда не обращается к внешнему CDN. Если локальная картинка всё же не загрузилась в браузере, `SlotArtwork` подставляет локальный `unavailable.svg`.

## Партнёрская интеграция

Настройки находятся только в `src/lib/affiliate.ts`, серверный переход — `/go/[operator]`. В `.env.local` можно определить `AFFILIATE_1WIN_URL` после проверки адреса и условий. Допускается только HTTPS; без адреса интерфейс показывает справочный переход, а `/go/1win` ведёт на disclosure. После изменения окружения для статических страниц нужна пересборка.

GEO Великобритании намеренно не включает партнёрский переход: локальная доступность 1win не заявлена. Для масштабирования GEO понадобится отдельная матрица оператор / страна / статус проверки. Произвольного URL-параметра для перенаправления нет.

## Проверки

```sh
npm run typecheck
npm run build
# Запустить npm start в отдельном терминале, затем:
npm test
node scripts/screenshots.mjs
```

Playwright использует установленный Chrome. Путь задаётся через `CHROME_PATH` в тестах; по умолчанию указан стандартный Windows-путь. Проверяются маршруты, внутренние ссылки, изображения, поиск, фильтры, сортировка, сравнение, SEO metadata / JSON-LD / sitemap / robots, FAQ, мобильное меню, 404, партнёрский fallback и переполнение на 320/390/768/1024/1440 px. Снимки и исследовательские изображения генерируются локально и в чистый GitHub-архив не входят.
